Design

From a business problem to an agent

A fictional shop, Nordlys Home, receives return, cancellation and refund emails. Finding the order and applying date-dependent rules is the slow part, so the design targets that step.

1 · ReadCustomer email, any language
2 · Look upOrder record, day counts
3 · DecidePolicy rules R1–R9
4 · CheckDraft vs facts
5 · Staff reviewApprove, revise or escalate

Why an agent

The next step depends on what a lookup returns: no order id, an order that is not the sender's, a shipped versus a delivered order. That is the test for an agent in the course's five-A menu. Automation and plain assistants were considered and compared against.

Controls

  • Two read-only tools, bound to the sender's email in code
  • Day counts computed by the tool, not the model
  • Max 6 steps, then one check of the draft
  • Refunds above 100 EUR cannot be approved by the agent
  • Email text is treated as untrusted data
  • Any failure routes to a human

Systems compared

  • B0 keyword templates
  • B1 paste email, order, policy; one call
  • B1d same, with precomputed day counts
  • Agent, no check tools and loop
  • Agent tools, loop and check

EDGE targets: Efficiency (staff minutes per ticket, modelled from assumptions, not measured) and Decisions (every reply grounded in the policy and the order record).

Results

Five systems, one ticket set

A ticket is a success only if the decision, cited rules, amount, language, claims and leak checks all pass. Checks are deterministic (regex and rules, no LLM judge), so they are reproducible but blunt. Intervals are 95% Wilson; with this few tickets they are wide. Staff minutes are modelled from assumed step times.

Run it

Reproduce everything

Python 3.10+ and pip install anthropic. Offline tests and the template baseline need no API key.

git clone https://github.com/louanbardou/refund-triage-agent.git && cd refund-triage-agent
python3 -m unittest discover -s tests -t .      # offline checks
python3 run_eval.py --systems b0                # offline baseline

export ANTHROPIC_API_KEY=...                    # live runs
python3 triage.py T06                           # one ticket, full trace
python3 run_eval.py --systems b0,b1,b1d,agent_nr,agent --label main
python3 -m refund_triage.site results/<run> --out docs   # rebuild this site

Limits. Author-written synthetic tickets, hand-labelled and cross-checked with a rule-based oracle; one small model (claude-haiku-5-5); regex-based scoring; modelled staff time; a short, unambiguous policy. The results suggest the design is feasible on clean cases. They do not show it would hold on a real inbox. A pilot would run in shadow mode with every draft approved by a person.
